# 0004. RLS y acceso a datos

Estado: Aceptado
Fecha: 2026-11-02
Issue: #1

## Contexto

La constitución exige RLS en toda tabla de negocio, pruebas contra Postgres real, `service_role` solo en el worker y aprobación humana para migraciones de producción. El plan usa Drizzle sobre el Postgres de Supabase. Drizzle con una conexión directa no aplica RLS por sí solo: hay que fijar el rol y la identidad en cada transacción.

## Decisión

### Acceso desde la app

- Todo acceso de `apps/web` a datos de negocio pasa por repositorios de `@hubly/db`, y cada consulta corre dentro de `withUserContext(claims, fn)`: una transacción que ejecuta `set local role authenticated` y `select set_config('request.jwt.claims', <claims>, true)` antes de `fn`.
- Las `claims` salen solo del JWT **verificado** por Supabase Auth en el servidor. Nunca de un encabezado, cookie sin verificar ni parámetro del cliente.
- Conexión por el pooler de Supabase en modo transacción, con sentencias preparadas desactivadas. `set local` vive solo dentro de la transacción, así que no se filtra entre peticiones.
- La cadena de conexión de la app no usa `service_role` ni un rol con `BYPASSRLS` para consultas de negocio. `service_role` queda reservado al worker (ADR futuro cuando exista).
- El cliente del navegador usa Supabase solo para Auth. No lee tablas de negocio por la Data API.

### Reglas en la base

- Toda tabla de negocio: `enable row level security` **y** `force row level security`. Sin política, nada pasa.
- Políticas separadas por operación (`select`, `insert`, `update`, `delete`) para el rol `authenticated`; ninguna para `anon`, y se revocan sus permisos sobre tablas de negocio.
- `insert` y `update` llevan `with check` además de `using`, para impedir crear o mover filas a otro espacio de trabajo.
- Membresía mediante una función `private.is_workspace_member(workspace_id)` `security definer`, `stable`, con `set search_path = ''`, en un esquema no expuesto. Las políticas usan `(select auth.uid())` para que se evalúe una vez por consulta.
- 1A: notas y pendientes exigen membresía **y** `created_by = (select auth.uid())` (privado por defecto, ADR 0003).

### Migraciones

- SQL versionado en `packages/db`; drizzle-kit puede generar el borrador, pero el SQL que se fusiona se revisa línea a línea. Las políticas viven en el mismo archivo que crea la tabla.
- Cada PR de migración incluye su reversión escrita o declara que es solo aditiva. Riesgo alto: requiere aprobación de Vega.
- Producción solo desde el entorno `production` de GitHub Actions, con aprobación del dueño. Ningún agente aplica migraciones fuera de Supabase local.

### Pruebas (llegan con la primera tabla, en 1A)

- Contra Supabase local en Docker, con dos personas en dos espacios de trabajo: B no puede leer, crear, modificar, borrar ni mover filas de A, ni insertar con el `workspace_id` de A.
- Un chequeo de catálogo falla si alguna tabla de `public` no tiene RLS activado y forzado o no tiene políticas.
- Una prueba de `withUserContext` comprueba que una petición sin claims no ve filas.

## Consecuencias

- La protección no depende de que cada repositorio filtre bien: si un caso de uso olvida un filtro, RLS lo detiene, y si RLS falla, la autorización del caso de uso lo detiene.
- Cada operación abre una transacción; para el volumen de 1A es aceptable y se medirá antes de optimizar.
- La Fase 0 no crea tablas ni corre pruebas de RLS; este ADR fija el contrato para que el primer PR de 1A lo cumpla desde el inicio.
